# 找选题

## 何时用

- 「找几个选题」「下一条拍什么」「这周拍啥」
- 候选池被采纳/否决后需要补充

## 先读什么

| 文件 | 用途 |
| --- | --- |
| `workbench/data/profile.json` | 赛道、人群、禁区——所有候选必须落在里面 |
| `workbench/data/topics.json` | `signals[]`（信号源）、`items[]`（现有候选）、`rejected[]`（否决过什么） |
| `workbench/data/account.json` | 哪些题材历史上完播高（别凭空猜） |
| `workbench/data/cards.json` | 可复用的钩子/结构卡，写进候选的 `cards` |

**信号源必须先有。** 如果 `signals[]` 少于 3 条，先告诉用户「信号不足，需要补评论/搜索/对标数据」，不要硬凑选题。

## 怎么做

1. **分三类信号**，不要混：用户需求（评论、搜索）、同行参考（对标爆款）、自有数据（历史表现）。同行在做什么 ≠ 用户想看什么。
2. **先排除**：`rejected[]` 里的题材不再提，除非用户明确说可以重做。
3. **出候选**：3–5 个，其中保守与激进的比例贴近 `topics.json.ratio`（默认 60/40）。
4. **五维打分**（0–100，越高越好）：
   - 需求：有多少人明确在问
   - 竞争：同类内容是否饱和（越高越好做）
   - 契合：是否符合定位与人群
   - 可证：你手上有没有真实案例/素材
   - 成本：制作成本（越高越省事）
5. **打分要能解释**：每个候选至少挂 1 条 `signals`，激进项必须在 `note` 里写风险。
6. **写回** `topics.json` 的 `items[]`，保留已有候选，不要覆盖用户已采纳的。

## 输出 schema

```json
{
  "id": "T-120",
  "score": 84,
  "title": "候选标题（用户会怎么问这个问题）",
  "note": "一句话依据，或激进项的风险",
  "mode": "保守",              // 保守 | 激进
  "modeTone": "svwb-g",        // 保守 svwb-g | 激进 svwb-a
  "dims": { "需求": 88, "竞争": 70, "契合": 90, "可证": 65, "成本": 55 },
  "signals": ["评论区 23 次同问", "搜索 +38%"],
  "cards": ["hook-20261026-01"],
  "status": "待排期"
}
```

`score` 用五维加权（需求 0.3、契合 0.25、竞争 0.2、可证 0.15、成本 0.1），四舍五入取整。

## 禁止

- 不许给没有信号来源的选题（那是拍脑袋）。
- 不许把同行爆款直接改写成候选——要说明「用户为什么关心」。
- 不许超过 5 个候选，也不许全是保守项。
- 不许动 `rejected[]`；否决权在用户。
- 宁可少给，也不要凑数。

## 完成后告诉用户

每个候选一行：标题 + 分数 + 一句依据。最后说「哪一条最值得先拍，为什么」。
